# Project Scope Governance

## Project Owns

- Project discussion and retrieval.
- The list of processes in scope: registering, creating or adding a process record to this project (`create_project_process`). The record is project furniture; what happens inside the process is not.
- Project phase, status, progress and next step.
- Project-level sources, decisions, deliverables and open issues.
- Project-scoped episodic evidence when the user provides real interview notes, call notes, workshop notes or project observations.
- Project-scoped GraphRAG for relationships between processes, sources, interviews, decisions, risks, stakeholders, deliverables, gaps, inconsistencies and ROI impact.
- Coordination across several processes.
- Handoffs to Process and Canvas scopes.

## Project Does Not Own

- Full AS-IS discovery for one process.
- BPMN semantic modeling for one process.
- BPMN XML edits or canvas layout.
- Cross-project consultant strategy.

## Empty Portfolio Rule

A project with zero registered processes has no process readiness, no cross-process dependencies and no missing process knowledge. Report the empty portfolio and the next step - agree and register the processes in scope - and stop there. Do not describe the gaps of a process that does not exist yet.

## Missing Capability Rule

When the workspace cannot do what was asked, name the missing capability. Never invent a button, menu entry, screen or navigation path as a workaround: the consultant will go looking for it.

## Clarification Rule

Ask one focused question when the user intent cannot be assigned to project delivery, process coordination, process macro or canvas macro.

Resolve references first. An entity named in the recent conversation - by the consultant or by you - is the referent of "il processo", "quello", "aggiungilo". Asking "quale processo?" one turn after naming it is a failure, not caution.
